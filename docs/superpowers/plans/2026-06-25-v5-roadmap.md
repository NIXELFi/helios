## Sequencing & dependencies

```
A (done) ──> B (backend + plugin:// hardening) ──┬──> C (member UI)
                                                  └──> D (review pipeline)
A (done) ──────────────────────────────────────────> E (MATLAB bridge)  [independent]
```

1. **B — Marketplace Backend & Distribution** *(first; everything else needs it)*.
   Also contains the **`plugin://` navigation-handler hardening** (Phase 0), which
   is the **blocker from spec §10**: it closes the self-navigation egress gap and
   MUST land before any *untrusted* (non-bundled) plugin is installable.
2. **C — Marketplace UI** and **D — Review Pipeline** both build on B's schema and
   can proceed in parallel once B's RPCs exist. Note: the `review_status` model + the
   approved-only gating live in **B** (C's list/install logic depends on B); **D** only
   adds the transition RPC that actually moves a version to `approved`. So C renders an
   empty browse until D approves something — do D's transition before relying on C's
   install button end-to-end.
3. **E — MATLAB engine bridge** is independent of B/C/D — it extends A's runtime +
   capability framework. It can start any time after A, but its install-time
   consent UX depends on C, and a Tier-2 plugin can't be *published to others*
   until D exists. Build the bridge mechanics anytime; gate public distribution on C+D.

Recommended single-threaded order: **B → D → C → E** (so untrusted install is never
possible before review exists). If two people are available: B, then C∥D, then E.

## Cross-cutting decisions (apply to all sub-projects)

- **One Supabase project, new schema.** Helios uses a single hosted Supabase project
  (`dlmyixonuyckxkknolku`). Add a new `marketplace` schema (parallel to `pdm`/`pm`),
  with migrations in **`infra/pdm-supabase/supabase/migrations/`** (the real location;
  use full 14-digit `YYYYMMDDHHMMSS_` filenames after the latest, `20260624000000`).
  **Expose the schema to PostgREST**: add `marketplace` to `schemas` + `extra_search_path`
  in `infra/pdm-supabase/supabase/config.toml` (for local), **and separately set the prod
  project's Exposed Schemas** — `supabase db push` does NOT carry that API setting. Apply
  migrations to prod via `supabase db push` (per `infra/pdm-supabase/README.md`), or the
  Management API `/database/query` endpoint when the DB is unreachable locally (see
  [[helios-v446-polish]] gotchas). The RLS/RPC test suite extends `infra/pdm-supabase/tests/`
  (and the `pdm.test_reset()` fixture must be extended to truncate `marketplace.*`).
- **Capability-gated, subteam-scoped.** Publishing and reviewing are new capabilities
  in the `pm.capabilities` catalog from [[unified-org-roles-initiative]]
  (`marketplace.publish`, `marketplace.review`), resolved by `pm.has_capability`.
  Installing is open to any signed-in member. Plugin *visibility* is scoped by owning
  subteam + org-wide.
- **Content-addressed bundles.** Store `.hplugin` zips in a Supabase Storage bucket
  keyed by sha256 (mirror the Vault's content-addressed model), so versions are
  immutable and de-duplicated.
- **Default-deny + tiers carry through.** The A trust tiers drive review depth: Tier
  0/1 plugins can be light-touch approved; Tier 2 (e.g. `engine:matlab`) requires
  human review (D) + install-time consent (C).
- **The validator is single-sourced.** Extract the bundle-scan rules from
  `packages/plugin-sdk/cli/helios-plugin.mjs` into a shared module both the CLI and the
  review pipeline (D) import — closes the drift risk noted in the A review (L5) and the
  spec §10. **Mechanism (the SDK has no build step):** author the canonical rules in a
  plain ESM `compliance.mjs` (so the Node `.mjs` CLI can `import` it directly) plus a
  hand-written `compliance.d.ts` for the TS consumers — avoids standing up an SDK
  build. (The host `loader.ts` only needs `validateManifest`, not the bundle scan; the
  scan is CLI + D.)

## Definition of done for v5.0.0

- A subteam Lead publishes a new version of their add-on from inside Helios; it lands
  in review (D); a reviewer approves it; members see it in the Marketplace (C),
  install it (B), and launch it sandboxed (A). A MATLAB-backed add-on (E) runs after
  an explicit consent screen. `main` stays releasable throughout; each sub-project
  merges behind the others on `feat/v5-plugin-runtime` (or its own feature branch).
