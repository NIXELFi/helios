# infra/telemetry-supabase

Cellular telemetry ingest pipeline for the shared Helios Supabase project:
schema `telemetry`, edge function `telemetry-ingest`, staging → parquet
compaction, plus bench bookkeeping tables. The Vault (`pdm`/`pm`/`games`)
schemas in the same project are **radioactive**: read-only for canary
queries, never written, never migrated, never locked.

Status: **authored, not yet verified** — no Docker on the authoring machine.
See `docs/telemetry-bench-HANDOFF.md` for the verification + deploy plan,
and `docs/telemetry-wire-protocol.md` for the wire format.

## Layout

- `supabase/migrations/` — the telemetry schema (isolated; reversible via
  `scripts/teardown.sql`)
- `supabase/seed.sql` — generated by `scripts/gen-seed.mjs` from
  `docs/channels.yaml`: channel registry + channel set 1 (`SDM26-cell-v1`,
  38 channels, 3 rate-homogeneous groups)
- `supabase/functions/telemetry-ingest/` — Deno edge function (HTP/1 binary
  + JSON fallback → Arrow IPC staging rows + Realtime Broadcast)
- `scripts/teardown.sql` — single-command teardown with before/after size

## Local stack

```sh
cd infra/telemetry-supabase
supabase start          # needs Docker
supabase db reset       # applies migrations + seed
supabase functions serve telemetry-ingest --env-file .env.local
```

For the S5 concurrency scenario (Vault canary under load) run the combined
stack instead: copy these migrations into `infra/pdm-supabase/supabase/
migrations/` (timestamps sort after all pdm migrations) and `supabase db
reset` there — that mirrors hosted exactly. The hosted apply uses the same
copy-then-push path; see the note at the top of `supabase/config.toml`.
